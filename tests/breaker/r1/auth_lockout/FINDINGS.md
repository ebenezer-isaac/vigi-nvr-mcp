# Breaker round 1 — vector auth-lockout — vigi-nvr-mcp @ db9f786
Model: claude-opus-4-8
Claim attacked: "In vigi-nvr-mcp, the authenticator and client can never issue more than one HTTP login attempt per explicit call; never auto-retry a failed login; perform zero network I/O when VIGI_NVR_LOGIN_DISABLED=true or when the breaker is open; re-authenticate at most once on a token-expiry (-40401/-40403 on /ds) and never on an auth failure; persist breaker state across process instances; and surface attempts_left/max_attempts/sec_left exactly as the device reports them."

Axes with no finding (confirmed_ok):
- State machine (login during login, token invalidated mid-call, expired token twice, second -40410, -40408 permanent lock, close-then-call). The `asyncio.Lock` in `Authenticator` plus the cached-token None-check serialise logins; `client.call` re-auths exactly once on `TokenExpired` and re-raises a second expiry (existing `test_second_expiry_after_reauth_is_raised_not_looped`, `test_failed_reauth_after_expiry_stops`). A second -40410 is recorded as a failure (`test_second_nonce_invalid_is_a_failure`); -40408 sets `locked=True`. `aclose()` closes the httpx transport, so a later `call` fails at the challenge POST before any login POST. Re-verified; nothing new.
- Concurrency (two coroutines on one client). Concurrent `token()` share one login and concurrent expiry re-auths exactly once (existing `test_concurrent_token_requests_share_one_login`, `test_concurrent_expiry_reauths_once`). A first-time concurrent login that fails lets only the first coroutine attempt; the second is refused by the budget. The auth lock covers auth; no login doubling found.
- Fail-open paths. No bare `except Exception: pass`. The only broad except is `core/tooling.py::run_tool`, which logs a traceback and returns an `INTERNAL_ERROR` envelope — it surfaces, it does not swallow. A transport error during login is counted as a failure (existing `test_transport_error_during_login_counts_as_failure`).
- Encoding edges (missing nonce/key, empty/unsupported/int encrypt_type). All raise before any login POST (existing `test_malformed_or_unsupported_challenge_never_attempts_login`; `encrypt_type` as ints is rejected by the `list[str]` model). The URL-encoded `key` is decoded once by the transport and not re-decoded. (Counter type-coercion is F3.)
- Clocks and durability of a breaker file. The breaker has no cooldown timer and never auto-reopens on time; `sec_left` is never used to schedule a retry. The "two processes / unwritable / corrupt / truncated JSON / missing state dir" sub-axis produced nothing additional only because there is no breaker file at all — that absence is itself F1.

## F1 Breaker state is not persisted across process instances — Impact 4 (a fresh process reopens the breaker and issues a new real login attempt against the device; repeated restarts or CLI reruns with wrong credentials drive the admin account into a hard lockout, leaving the device unreachable until the lock expires or a human intervenes; evidence: `core/breaker.py` holds only an in-memory `LoginLedger`, no file I/O exists anywhere in the package except config backups, and there is no `VIGI_NVR_STATE_DIR` nor a `breaker --clear` CLI command) × Likelihood 3 (debugging a failing login is exactly when an operator reruns `vigi-nvr-mcp --check-auth --login`, a new OS process each time, which the CLI provides precisely for this; the systemd deploy target in MASTER-PLAN §6 also restarts services; adversary-reading? no) = 12 Critical
Test: tests/breaker/r1/auth_lockout/test_breaker_persistence.py::test_breaker_stays_open_after_process_restart
Test: tests/breaker/r1/auth_lockout/test_breaker_persistence.py::test_cli_check_auth_login_reruns_are_breaker_limited
What happens: one process fails a login (budget of 1 spent; in-process the breaker correctly blocks further logins). A second Authenticator/`NvrBackend` built from the identical device settings, standing in for the next process invocation, starts with `failed=0` and issues a fresh login POST to the device (`fake2.login_attempts == 1`, `LockoutGuard` not raised). Nothing on disk remembers the earlier failure, so there is no cross-process lockout protection and no way for a human to clear a breaker that never persisted. The claim ("persist breaker state across process instances"), spec 01-NVR-SPEC §N1 ("failed login -> breaker written") and MASTER-PLAN §1.3 ("a persistent breaker (file under <PREFIX>_STATE_DIR ...) that blocks further logins after a failure until a human clears it (breaker --clear)") are all unmet.
Why (root cause hypothesis): the breaker was implemented as a per-process in-memory ledger; the persistence layer (state-dir JSON file plus `breaker --show|--clear` CLI) specified in MASTER-PLAN §3 was never built.

## F2 Pre-login lockout guard discards the device challenge counters — Impact 2 (when the account is already locked, the error tells the owner it is locked but drops the `sec_left` countdown and `max_time`, so he cannot see how long to wait; a visible failure he can get past; evidence: `LockoutGuard` carries no counter attributes and `details()` returns `{}`) × Likelihood 2 (requires the account to be locked and the device to report counters in the pre-auth challenge, reachable after repeated bad logins; adversary-reading? no) = 4 Minor
Test: tests/breaker/r1/auth_lockout/test_lockout_counters.py::test_prelogin_lockout_surfaces_sec_left_and_max
What happens: the challenge reports `time=0, max_time=10, sec_left=1740`. `check_remaining_attempts` reads only `challenge.time`, raises a bare `LockoutGuard` ("...0 login attempts remaining..."), and the device-reported `max_attempts` and `sec_left` are dropped entirely (`details() == {}`). The claim says these are surfaced "exactly as the device reports them"; on this path none of them are structured data.
Why (root cause hypothesis): `check_remaining_attempts` passes only the remaining-attempts integer and `LockoutGuard` was never given the counter fields that `AuthFailed` has.

## F3 String-typed login-failure counters are silently dropped to null — Impact 2 (the counters are reported as `null` instead of the device values, so a tool answer the owner or LLM reads understates the lock state; evidence: `_int_or_none` returns `None` for any non-`int`) × Likelihood 1 (no measurement that the firmware failure reply uses string counters; the authenticator's own `Challenge` model accepts strings via pydantic lax coercion, so the shape is anticipated but unproven on the failure path; adversary-reading? no — a MITM that controls the reply controls the whole envelope anyway) = 2 Won't-fix
Test: tests/breaker/r1/auth_lockout/test_lockout_counters.py::test_login_failure_string_counters_are_surfaced
What happens: a -40404 login reply carries `data.time/max_time/sec_left` as the strings "0"/"10"/"1740". `_record_failure` runs each through `_int_or_none`, which rejects non-`int`, so `AuthFailed.lock_seconds_left/max_attempts/attempts_left` are all `None`. The challenge path would coerce the same strings to ints; the failure path does not — an inconsistency, scored Won't-fix pending a LIVE capture showing the firmware failure replies use strings.
Why (root cause hypothesis): `_record_failure` parses raw dict values with a strict `isinstance(int)` guard instead of the lax coercion the `Challenge` model uses.

## F4 Challenge/healthcheck still perform network I/O when login is frozen — Impact 1 (a harmless pre-auth challenge POST; it spends no login attempt and nothing the owner would act on; evidence: `get_challenge` sends the `/` path and returns normally) × Likelihood 4 (every `nvr_status` or `--check-auth` call takes this path; adversary-reading? no) = 4 Minor
Test: tests/breaker/r1/auth_lockout/test_login_disabled_io.py::test_get_challenge_makes_no_io_when_login_disabled
Test: tests/breaker/r1/auth_lockout/test_login_disabled_io.py::test_check_auth_makes_no_io_when_login_disabled
What happens: with `VIGI_NVR_LOGIN_DISABLED=true`, `Authenticator.get_challenge`, and therefore `backend.check_auth(login=False)` and `backend.healthcheck`, still POSTs the pre-auth challenge to the device (`fake.requests == ['/']`). The claim ("perform zero network I/O when VIGI_NVR_LOGIN_DISABLED=true") and spec 01-NVR-SPEC §N1 line 25 ("Honour login_disabled and breaker before any network call") and line 32 ("login_disabled -> no HTTP call at all") are literally violated, though only by a pre-auth probe. The same holds when the breaker is open (no `check_login_allowed` call guards `get_challenge`).
Why (root cause hypothesis): the `login_disabled`/breaker guard lives in `_login_locked`, not in `get_challenge`, so the healthcheck path bypasses it.

## F5 One explicit login can send two login HTTP POSTs on -40410 — Impact 2 (a second password-bearing login POST reaches the device unasked; harmless if the firmware does not count a nonce-rejected POST, but that is not live-verified; if it does count, each call spends two attempts toward lockout; evidence: existing `test_nonce_invalid_rechallenges_exactly_once` asserts `login_attempts == 2`) × Likelihood 2 (natural -40410 is rare, but `verify_tls` defaults to False, so a LAN MITM can return -40410 to force the extra POST; adversary-reading? yes — reachable for someone who wants it, though the local breaker caps it at two per process) = 4 Minor
Test: tests/breaker/r1/auth_lockout/test_one_login_per_call.py::test_single_explicit_login_sends_at_most_one_login_post
What happens: the first login POST is answered -40410; `_login_locked` fetches a fresh challenge and POSTs the login a second time within the same explicit `login()` call (`fake.login_attempts == 2`). The claim ("never more than one HTTP login attempt per explicit call") and spec 01-NVR-SPEC §N1 line 25 ("login() -> Token (exactly one HTTP login)") are violated. Would rise to Major if a LIVE test shows the firmware counts a nonce-rejected POST toward the lockout counter (combine with F1 missing persistence to reach a full lockout across restarts).
Why (root cause hypothesis): the -40410 "password was never evaluated" carve-out re-invokes `_attempt`, which sends another real login POST, on the unverified assumption the device ignores it.
