# Breaker round 2 — vector auth-persist — vigi-nvr-mcp @ 0295583
Model: claude-opus-4-8
Claim attacked: "In `vigi-nvr-mcp` @ `0295583`, lockout state persists across process instances via a per-host JSON file under `VIGI_NVR_STATE_DIR` (default `~/.local/state/vigi-nvr-mcp/`), written atomically with mode 0600 and loaded on every check; a corrupt, truncated, unreadable, unwritable or wrongly-typed state file makes login impossible with a clear `BreakerOpen` error (fail closed); `breaker --show|--clear` work and `--clear` is the only way to reopen after a failure; exactly one login POST per explicit `login()` (`-40410` raises `NonceInvalid`, not counted, not resent); `LOGIN_DISABLED` blocks every login POST but allows the challenge probe; `LockoutGuard` carries `attempts_left/max_attempts/sec_left`; nothing in the state file or its error messages contains a secret."

Round-1-on-round-1 signal: **YES — all three findings sit on the fixer's new code.** R1 found the breaker was in-memory; the fix added the whole file-backed `LoginBreaker` (`core/breaker.py` `_load`/`_save`/`check`/`show`, per-host file naming, `breaker --show|--clear`). All seven failing tests below exercise that new code, not untouched modules. The R1 auth_lockout suite (`tests/breaker/r1/auth_lockout/`) now passes (7/7), so R1-F1 (persistence), R1-F2 (LockoutGuard counters), R1-F4 (login-disabled I/O clarified allowed) and R1-F5 (double POST on -40410) are genuinely fixed — the problems that remain were introduced by, or newly exposed in, the persistence layer the fix built.

Axes with no finding (confirmed_ok, with evidence):
- **One login POST per explicit `login()` / `-40410`.** R1-F5 is fixed: `_login_locked` now raises `NonceInvalid` on `NONCE_INVALID` with no resend and no `record_failure` (`auth.py:143-152`); `_attempt` sends exactly one challenge + one login POST. Nonce rejection is not counted. Confirmed by the passing R1 `test_one_login_per_call.py`.
- **`LOGIN_DISABLED` blocks login POSTs, allows the challenge.** `check_login_allowed` raises `LockoutGuard` on `login_disabled` before `_attempt`, on both the explicit and implicit paths; `get_challenge` is deliberately unguarded (spec §1.3 clarification). No bypass to a login POST exists — `_login_locked` is the sole caller of `_attempt` and always calls `check()` first.
- **`LockoutGuard` carries counters.** R1-F2 fixed: `LockoutGuard.__init__`/`details()` carry `attempts_left/max_attempts/sec_left` (`errors.py:149-168`) and `check_remaining_attempts` passes them through.
- **Secrets in the state file / error strings.** `_save` writes only `device` (host), `failed`, `successful`, `last_failure`; `last_failure` is the 4-key dict from `_record_failure` (`device_error_code/attempts_left/max_attempts/lock_seconds_left`) — no password, token, nonce or ciphertext. Error messages contain env-var names, counts and the state path only. Nothing credential-bearing reaches the file or the messages.
- **Clocks / `sec_left` arithmetic.** The breaker has no cooldown and performs no time arithmetic; `sec_left` is passed through from the device untouched. Negative/zero/huge values flow through `check_remaining_attempts` (`remaining <= 0`) without miscomputation. Nothing.
- **State file is a directory / disk full mid-write / unwritable dir.** All fail closed correctly: a directory at the path makes `read_text` raise `OSError` -> `BreakerOpen` on load and `os.replace` raise `OSError` -> `BreakerOpen` on save; `json.dump`/`os.open` `OSError` (ENOSPC, EACCES) -> `BreakerOpen`; the tmp file is unlinked and the live file left intact. Correct fail-closed behaviour.
- **Symlinked state file.** `os.replace` overwrites the symlink itself (no target traversal); a planted symlink only matters to someone who already has write access to the state dir, which is the trust boundary — no privilege elevation. Nothing exploitable.
- **Extra / future-version keys.** Unknown keys are ignored by `_load` (forward-compatible); not a defect. (A *future-version type change* of a numeric field is the F2 case.)
- **`--clear` is the only way to reopen after a failure.** A successful login does NOT reset `failed` (`record_success` only bumps `successful`), consistent with the spec's "until a human clears it". Note (not scored): raising `VIGI_NVR_MAX_LOGIN_FAILURES` in env reopens a tripped breaker without `--clear`, and with a budget > 1, failures accumulate across intervening successful logins (a success never clears them) until the breaker trips despite proven-good credentials — both need a non-default budget; recorded as an observation, no test.
- **Atomic write / mode 0600 on Windows.** `os.open(..., 0o600)` and `mkdir(mode=0o700)` are POSIX-only; on the Windows dev host the mode is effectively ignored (file inherits the dir ACL). The deploy target is Ubuntu (MASTER-PLAN §6), so this is a dev-only caveat, not a finding. Separately, `mkdir(mode=0o700, parents=True)` applies 0700 only to the leaf dir; intermediate parents (`~/.local`, `~/.local/state`) are created with the umask default — minor, unscored (the file itself is 0600 and holds no secret).

## F1 Concurrent processes bypass the one-failure budget (lock-free read-modify-write => lost update) — Impact 3 (two or more real wrong-credential login POSTs reach the device under a budget that should permit one, and the saved counter under-reports the attempts, so a crash-loop of overlapping processes keeps re-opening the breaker and can walk the admin account into the hard device-side lockout the breaker exists to prevent, leaving the NVR unreachable until the lock expires or a human intervenes; evidence: the file protocol has no cross-process lock — `check()`->`_load()` and `record_failure()`->`_load();_save()` take no `flock`/`msvcrt` lock; the test records two distinct failures and the file keeps `failed=1`, and two concurrent `login()`s both POST under `max_login_failures=1`) x Likelihood 2 (needs overlapping invocations — an operator double-running `--check-auth --login`, or a supervisor/systemd restart that overlaps a still-exiting instance; an uncommon combination, not the everyday path. Adversary-reading? yes for the goal case: an LLM client or compromised LAN host that *wants* to lock the owner out can deliberately fire parallel logins, for which the state is fully reachable — scored on the ordinary case here) = 6 Major
Test: tests/breaker/r2/auth_persist/test_concurrent_budget.py::test_lost_update_two_processes_record_only_one_failure
Test: tests/breaker/r2/auth_persist/test_concurrent_budget.py::test_two_concurrent_logins_both_reach_the_device
What happens: two `LoginBreaker`s for one host both `check()` an empty ledger (both pass, `failed=0`), each records a failed login; because `record_failure` loads before the other has saved, the file ends at `failed=1` after two real failures (lost update). The async test confirms the device-facing effect: two `Authenticator.login()`s run in lock-step (a shared `asyncio.Barrier` holds both past `check` before either records, exactly as two parallel OS processes behave) and **both** send a login POST — `fake1.login_attempts + fake2.login_attempts == 2` under `max_login_failures=1`, with both raising `AuthFailed` (neither blocked by the breaker). The persistent breaker closes the *sequential* restart hole (R1-F1) but not the *concurrent* one.
Why (root cause hypothesis): the persistence layer serialises nothing across instances — there is no file lock and the load-decide-act / load-modify-write sequences are not atomic — so the "one fact" (the failure count) is read and written by concurrent holders without reconciliation.

## F2 A wrongly-typed state file does not fail closed with `BreakerOpen` — uncaught exception, `--show` crash, and a fail-open case — Impact 3 (the claim's fail-closed guarantee is broken three ways: `{"failed":"oops"}` raises an uncaught `ValueError` and `{"failed":[1]}` an uncaught `TypeError` — not the promised `BreakerOpen`, so `breaker --show` (which catches only `BreakerOpen`) dies with a traceback right when an operator is diagnosing a stuck breaker, and the tool path turns it into `INTERNAL_ERROR` with the wrong CLI exit code instead of `BREAKER_OPEN`->3; worse, `{"failed":false}` coerces to `int(False)==0` and the breaker reads zero failures and **FAILS OPEN**, allowing a login a corrupt state should have refused; evidence: the four failing tests below) x Likelihood 1 (the atomic writer never emits these shapes itself, so the file must come from a manual edit, a foreign tool, or a future schema that retypes a numeric field; no evidence it occurs in the field today) = 3 Minor

Test: tests/breaker/r2/auth_persist/test_corrupt_state_file.py::test_show_does_not_crash_on_wrongtyped_file
What happens: `LoginBreaker._load` wraps only `json.loads` in `try/except (OSError, ValueError)`; the following `int(data.get("failed", 0))` / `int(data.get("successful", 0))` coercions are unguarded. A valid-JSON file whose numeric field is a non-numeric string raises `ValueError` past the guard; a list/null raises `TypeError` (not even in the caught set); a JSON `false` silently becomes `0` and defeats the breaker. None of these produce the "clear `BreakerOpen` error (fail closed)" the claim promises, and the `false` case is an outright fail-open.
Why (root cause hypothesis): `_load` validates only that the top level is a dict and that JSON parses, then trusts the field types; the coercion `int(...)` does the real type-checking but outside the fail-closed `except`, so any wrongly-typed field either escapes as a raw exception or, for falsy/fractional values, degrades to `0`.

What happens: `LoginBreaker(dir, "fe80::1", s)` and `LoginBreaker(dir, "fe80:0:0:0:0:0:0:1", s)` resolve to `breaker-fe80__1.json` and `breaker-fe80_0_0_0_0_0_0_1.json`; `ipaddress` treats the two as the same address and both pass `validate_host`, yet exhausting the budget on the first leaves the second fully open.
